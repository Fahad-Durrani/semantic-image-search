# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local semantic image-search app over ~7,810 images. Images are embedded once with **Apple's official MobileCLIP** (the `mobileclip` package from github.com/apple/ml-mobileclip), using four switchable checkpoint variants — **S2** (`mobileclip_s2.pt`, the original/default), **S0** (`mobileclip_s0.pt`, added later), **S0-fp16** (`mobileclip_s0_fp16.pt`, a half-precision export of the same S0 architecture, added after that), and **S0-int8** (`mobileclip_s0_image_int8.pt` + `mobileclip_s0_text_int8.pt`, a pair of separately int8-quantized TorchScript encoders for the same S0 architecture, added after that) — plus two genuinely different model families from wkcn's **TinyCLIP** project, added after that: **TinyCLIP-ViT-8M/16** (`wkcn/TinyCLIP-ViT-8M-16-Text-3M-YFCC15M`, loaded via HuggingFace `transformers`) and **TinyCLIP-ResNet-19M/Text-19M** (`TinyCLIP-ResNet-19M-Text-19M-LAION400M.pt`, loaded via `open_clip` with a custom registered config and a remapped checkpoint — the only variant with a 1024-d embedding space instead of 512). A Flask server then encodes text queries — or an uploaded/selected image — with whichever model is selected and ranks images by cosine similarity. The frontend (search, autocomplete, similar-image, drag-and-drop upload, lightbox, model dropdown) is a single HTML string embedded in `app.py`.

> Note: an earlier version used open-clip-torch's `MobileCLIP2-S2` (`dfndr2b`) weights from HuggingFace. That was abandoned because it applies a different image normalization than Apple's. Do **not** reintroduce open_clip for model loading — use the `mobileclip` package so the normalization matches.

## Directory layout (paths are hardcoded in both scripts — keep in sync)

- `images_repo/` — the flat image library, files named `1.jpg … 7811.png`. Served by `GET /images/<filename>`.
- `checkpoints/mobileclip_s2.pt`, `checkpoints/mobileclip_s0.pt`, `checkpoints/mobileclip_s0_fp16.pt` — Apple checkpoints (S2 ~380 MB, S0 ~215 MB, S0-fp16 ~108 MB, not in git). `checkpoints/mobileclip_s0_image_int8.pt` (~13 MB) + `checkpoints/mobileclip_s0_text_int8.pt` (~44 MB) — a *pair* of quantized checkpoints for S0-int8, also not in git. `checkpoints/tinyclip-vit-8m-16-text-3m-yfcc15m/` — a local HF-hub snapshot directory (config.json, tokenizer.json, model.safetensors, preprocessor_config.json, ~90 MB), also not in git. `checkpoints/tinyclip_resnet19m_text19m_laion400m.pt` (~121 MB, raw open_clip-format checkpoint) + `checkpoints/TinyCLIP-ResNet-19M-Text-19M.json` (the open_clip model config it's registered under), also not in git.
- `cache/embeddings.npz` (S2) / `cache/embeddings_s0.npz` (S0) / `cache/embeddings_s0_fp16.npz` (S0-fp16) / `cache/embeddings_s0_int8.npz` (S0-int8) / `cache/embeddings_tinyclip.npz` (TinyCLIP-ViT-8M/16) / `cache/embeddings_tinyclip_resnet19m.npz` (TinyCLIP-ResNet-19M/Text-19M) — built indexes. **Each has two aligned arrays: `embeddings` (N×D float32, L2-normalized, D=512 for every variant except tinyclip_resnet19m where D=1024) and `filenames` (bare names).** Note the key is `filenames`, not `paths`.
- `cache/suggestions.json` (S2) / `cache/suggestions_s0.json` (S0) / `cache/suggestions_s0_fp16.json` (S0-fp16) / `cache/suggestions_s0_int8.json` (S0-int8) / `cache/suggestions_tinyclip.json` (TinyCLIP-ViT-8M/16) / `cache/suggestions_tinyclip_resnet19m.json` (TinyCLIP-ResNet-19M/Text-19M) — autocomplete counts, auto-rebuilt when `VOCAB` changes (keyed by an md5 hash of the vocab). Counts differ per model since they're derived from that model's embeddings.
- `ml-mobileclip/` — cloned Apple repo, installed editable. Must persist (editable install references it).
- `build_index.py`, `app.py` — the two entry points. Both define a `MODEL_CONFIGS = {"s2": {...}, "s0": {...}, "s0_fp16": {...}, "s0_int8": {...}, "tinyclip": {...}, "tinyclip_resnet19m": {...}}` dict mapping a short key to `{model_name, checkpoint, cache_file}` (`app.py`'s entries also carry `label`/`suggestions_file`) — **keep these two dicts in sync** when adding another variant. The `s0_fp16` entry additionally carries `"reparam_checkpoint": True`; the `s0_int8` entry carries `"quantized": True` and a `checkpoint` that's a `{"image": ..., "text": ...}` dict instead of a single path; the `tinyclip` entry carries `"hf_clip": True` and a `checkpoint` that's a local directory path, not a file; the `tinyclip_resnet19m` entry carries `"open_clip_config"` (path to its registered model config JSON) and `"embed_dim": 1024` (see below).

## Architecture

All entry points share the same L2-normalization at query time, so cosine similarity is a plain dot product regardless of model. S2, S0, S0-fp16, S0-int8, and TinyCLIP-ViT-8M/16 all use the same embedding dimensionality (512), so nothing downstream needs to special-case shape for them — this is coincidental (TinyCLIP is an unrelated model family, not resized to match). **TinyCLIP-ResNet-19M/Text-19M is the exception: its `embed_dim` is 1024.** Nothing in `app.py`/`build_index.py` hardcodes 512 anywhere in actual logic (verified by grepping the whole codebase, not just these two files) — every embeddings array/query-vector pairing (`run_search`, `encode_text`, `encode_image_pil`, the `/rebuild` incremental-append path) is scoped to one model's own matrix and never mixed across models, so a differently-sized model drops in safely. Any *future* variant with yet another dimensionality would be equally safe for the same reason.

- **`build_index.py`** — offline indexer, takes `--model {s2,s0,s0_fp16,s0_int8,tinyclip,tinyclip_resnet19m}` (default `s2`). Loads that variant from its checkpoint via the shared `load_model()` helper, batches images (`BATCH_SIZE=32`) through `encode_image`, L2-normalizes, writes that variant's `cache_file`. Per-image try/except skips corrupt files (e.g. `4784.jpg`), so `len(filenames)` can be one or two less than the file count on disk. Run it once per model you want available.
- **Loading a checkpoint** (`load_model()` in `build_index.py`, `_load_model()` in `app.py` — same logic, kept separately per file): `mobileclip.create_model_and_transforms(..., pretrained=CHECKPOINT)`'s default path expects a checkpoint whose keys match the model's *unreparameterized* (multi-branch `rbr_conv`/`rbr_scale`) MobileOne structure, and folds the branches into `reparam_conv` itself *after* loading. `mobileclip_s0_fp16.pt` was exported *after* that folding already happened (its keys are `reparam_conv`, in fp16), so loading it needs the opposite order: build the model with `reparameterize=False`, call `reparameterize_model()` on it *first* to get matching `reparam_conv` keys, then `load_state_dict()` the fp16 weights into it (PyTorch casts fp16→fp32 automatically; verified ~0.9999 cosine agreement against the fp32 S0 checkpoint on both text and image encodes). Any future checkpoint that's a "folded" export needs the same `reparam_checkpoint: True` treatment; anything shaped like the original Apple release doesn't.
- **S0-int8 loading is a different shape entirely**: `mobileclip_s0_image_int8.pt` / `mobileclip_s0_text_int8.pt` aren't state dicts at all — they're self-contained `torch.jit.load()`-able TorchScript `RecursiveScriptModule`s (int8-quantized via fbgemm/qnnpack), one per encoder, each directly callable as `model(tensor)` and already returning L2-normalized 512-d float32 output. A `_QuantizedDualEncoder` wrapper (defined in both files) exposes `.encode_image()`/`.encode_text()` over the pair so the rest of the code doesn't need to know it's not a real `CLIP` model. Quantized ops only run on CPU (no CUDA kernels for fbgemm/qnnpack), so this variant's `device` is forced to `"cpu"` regardless of `torch.cuda.is_available()`. The image/text transforms and tokenizer are still fetched the normal way (architecture-derived, not weight-derived). Verified cosine agreement against fp32 S0 is much lower than fp16's (~0.84 image / ~0.70 text vs. ~0.9999) — expected for int8, and the whole point of exposing it side-by-side for comparison rather than assuming it's a drop-in replacement.
- **TinyCLIP-ViT-8M/16 is loaded via a completely different library**: `wkcn/TinyCLIP-ViT-8M-16-Text-3M-YFCC15M` is a standard HuggingFace `transformers` `CLIPModel`/`CLIPProcessor` checkpoint (safetensors, ~23M params) — not a `mobileclip` model at all, so none of the mobileclip loading machinery (reparameterization, MobileOne blocks, `mobileclip.get_tokenizer`) applies. It's loaded with `CLIPModel.from_pretrained(local_dir, local_files_only=True)` from the local snapshot directory (never hits the network at runtime). `_HFClipEncoder`/`_HFImageTransform`/`_HFTextTokenizer` wrappers (defined in both files) adapt HF's API (`get_image_features()`/`get_text_features()`, which return an output object with `.pooler_output` on newer `transformers` versions or a plain tensor on older ones — handled defensively) to the same `.encode_image()`/`.encode_text()`/tokenizer-callable/`image_transform`-callable interface the rest of the code uses, so `_load_model()` had to start returning the tokenizer too (previously `app.py` always fetched it separately via `mobileclip.get_tokenizer(model_name)` after the call, which doesn't exist for this variant). Preprocessing (resize/crop/normalize) comes from `CLIPProcessor`'s `image_processor`, using the standard OpenAI CLIP mean/std — not Apple's normalization, since this isn't Apple's model. `transformers` is only needed if this variant is enabled (see `requirements.txt`).
- **TinyCLIP-ResNet-19M/Text-19M is loaded via `open_clip` -- yet a third library/pattern**: this is a raw checkpoint from wkcn's TinyCLIP GitHub releases (not HuggingFace), in `open_clip`'s native format, using a `ModifiedResNet` vision tower (standard CLIP-style ResNet-50 shape, `layers: [3,4,6,3]`, uniformly scaled to `width: 44`) rather than a ViT. Two things had to be figured out and verified before this was safe to wire in:
  1. **The model config isn't built in** to vanilla `open_clip` -- it has to be registered at runtime via `open_clip.add_model_config(json_path)` (the `open_clip_config` field in `MODEL_CONFIGS`), pointing at a config JSON pulled from `wkcn/TinyCLIP`'s fork of `open_clip`'s `model_configs/` directory. That JSON's filename stem becomes the registered model name, so `"model_name"` in `MODEL_CONFIGS` must match it exactly.
  2. **The raw checkpoint's state dict keys don't match `open_clip`'s `CLIP` class at all** -- they're wrapped under a training-time DDP prefix that varies by release (observed forms: `"image_encoder_without_ddp."`, `"_image_encoder.module."`, `"text_encoder_without_ddp."`, `"_text_encoder.module."`, `"_logit_scale.module.(module.)?logit_scale"`). `_remap_tinyclip_open_clip_key()` (defined in both files) strips these via regex before `model.load_state_dict()`; verified **zero** missing/unexpected keys against the actual checkpoint (not just a plausible-looking config -- see the next point for why that check matters).
  3. **Not every TinyCLIP release is loadable this way.** wkcn's model zoo has both "Manual" (uniformly-scaled, like this one) and "auto inheritance" variants (independently pruned per-layer, e.g. `TinyCLIP-ViT-22M-32-Text-10M`, considered and rejected for this project) -- the latter have a *different* width at every single transformer block/conv layer (verified directly: MLP hidden dims of 789/1999/815 across three checked vision blocks), which `open_clip`'s uniform-width model classes cannot represent at all, config or no config. Loading one of those would require vendoring wkcn's custom fork's model-building code, not just a JSON + prefix strip. Before trusting a config file's `vision_cfg`/`text_cfg` for any future TinyCLIP addition, actually download the checkpoint and check whether same-stage layer shapes match across blocks -- a clean-looking config is not sufficient proof by itself.
  4. Since `open_clip`'s own `CLIP` class already implements `.encode_image()`/`.encode_text()`, and `open_clip.get_tokenizer()`/the `preprocess` transform returned by `create_model_and_transforms()` already match this project's calling convention exactly, **no wrapper classes were needed** for this backend (unlike `_QuantizedDualEncoder`/`_HFClipEncoder` for the other two non-native backends).
- **`app.py`** — Flask server. On startup loops over `MODEL_CONFIGS` and loads **all configured** models simultaneously into a `MODELS` dict (keyed by model key, each holding its own `embeddings`/`filenames`/`model`/`tokenizer`/`image_transform`/`device`), so requests can switch models with no restart. It also kicks off a background thread to build the **colour palette index** (shared across models — built from raw pixels, not embeddings) and builds a suggestion + prefix index **per model** (encodes the ~500-term `VOCAB` once against each model's embeddings). Endpoints: `/search` (text, supports `-negative` terms, `&color=`, `&model=s2|s0|s0_fp16|s0_int8|tinyclip|tinyclip_resnet19m`), `/similar` (by indexed filename, `&model=`), `/search_by_image` (POST upload, `&model=`), `/suggest` (autocomplete, `&model=`), `/models` (list of `{key, label, default}` from `MODEL_CONFIGS` — what the frontend populates every model dropdown/panel from, so adding a model server-side needs no frontend change), `/colors` (available colour names, model-agnostic), `/rebuild` (POST, starts incremental re-index for **all** models together) + `/rebuild_stream` (SSE progress), `/images/<f>`, `/`.
- The single-page frontend (in `FRONTEND_HTML`) has two top-level views toggled by the **Compare Models** header button (`compareMode`, persisted): **single view** (`#singleView`, the original layout) with a **model dropdown** (populated from `/models`, persisted via `localStorage`), autocomplete, **recent searches** (localStorage), **colour filter bar**, lightbox, find-similar; and **compare view** (`#compareView`) with a shared query/Top K/colour-filter bar and a row of independent model panels (`comparePanels`, persisted) — each panel has its own model `<select>` and remove button, queries `/search` independently with the shared query but its own `model=`, and panel count is capped at `MODEL_LIST.length` so "+ Add model" naturally scales as more models are added to `MODEL_CONFIGS` (this is how `s0_fp16`, `s0_int8`, `tinyclip`, and `tinyclip_resnet19m` show up in both views with zero frontend changes). Card rendering (`buildCardsHTML`) and click wiring (`wireCardClicks` → lightbox / "Similar") are shared between both views. Also: **dark mode** toggle (CSS variables + `[data-theme="dark"]`, persisted) and a **Rebuild Index** modal driven by the SSE stream.

### Extra cache files (besides the per-model embeddings*.npz / suggestions*.json)
- `cache/colors.json` — `{filename: [dominant colour names]}`, built once by an HSV scan (`_extract_dominant_colors`, 25×25 downscale). Powers the colour filter. Shared across models.
- `cache/skip_list.json` — filenames that failed to open during a rebuild, so they aren't retried (e.g. corrupt `4784.jpg`). Shared across models.

### Things that will bite you

- **`model.eval()` is mandatory** — MobileCLIP has batchnorm; skipping eval mode silently corrupts embeddings. True for every variant (for S0-int8, `.eval()` is forwarded to both wrapped TorchScript modules; for TinyCLIP-ViT-8M/16, to the wrapped HF `CLIPModel`; TinyCLIP-ResNet-19M/Text-19M's ResNet vision tower has batchnorm too, same rule applies to the plain `open_clip.CLIP` instance).
- **Index ↔ filename alignment**: row `i` of a model's `embeddings` ↔ that model's `filenames[i]`. `build_index.py` (full rebuild) and `/rebuild` (incremental, appends new files only, run for all models together) both keep them aligned and re-save each model's npz. If you ever build one model's index separately from the others, their `filenames` arrays can end up covering different file sets — the app doesn't detect or guard against this.
- **Search is pure relevance order** (`run_search`) — the old MMR/diversity, expand, and re-rank features were removed per user request. Dedup is kept. `run_search` now takes a `model_key` and reads that model's embeddings/filenames from the `MODELS` dict.
- **Score range**: MobileCLIP text-image cosine sims run ~0.2–0.31 for good matches for S2, not near 1.0; S0 (a smaller model) may have a somewhat different typical range. S0-fp16 is the same architecture and weights as S0 (just lower precision, ~0.9999 cosine-agreement with the fp32 checkpoint), so its score range should track S0's closely. S0-int8 is a much lossier quantization (~0.84/0.70 cosine-agreement with fp32 on image/text) so its scores and rankings can meaningfully diverge from S0's — that divergence is the point of having it available to compare, not a bug. **TinyCLIP-ViT-8M/16's baseline cosine similarity runs much higher across the board** (~0.35 even for a gibberish query, vs. S2's ~0.2–0.3 for a real one) since it's an unrelated model trained differently — this also means the fixed `SUGGEST_THRESHOLD` (0.20) used to build autocomplete counts is miscalibrated for it specifically, so its autocomplete counts skew high (most terms show a count close to the full image total) even though relative *ranking* for an actual search is still meaningful. **TinyCLIP-ResNet-19M/Text-19M** is a 1024-d space with its own unrelated scale on top of that (checked with a known lion image: "a lion" ~0.33, "a bicycle" ~0.15, gibberish ~0.16 — a clean, sensible separation, but the raw numbers aren't comparable to any other model's). The UI normalizes the bar width to the top hit's score, so none of this is hardcoded anywhere in app logic — just worth knowing when eyeballing raw scores or counts across models.
- **Dedup**: near-identical images (cosine > `DEDUP_THRESHOLD` 0.999) are collapsed into one result with a `+N identical` badge rather than shown separately.
- **No FAISS** — search is plain numpy matmul over each model's own (N×D) matrix; fast enough at this scale. (faiss-cpu was deliberately not installed.)
- **Colour filter** is applied by zeroing scores of images whose `colors.json` entry lacks the chosen colour, before ranking. Unaffected by which model is selected.
